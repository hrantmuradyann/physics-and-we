# CLAUDE.md

Technical map of this repo for Claude Code (or any AI agent) starting a fresh session. Human docs live in `README.md` (long, narrative, onboarding-focused) and `Instructions/` (task-specific guides); this file is the dense/skimmable equivalent for an agent — architecture, file map, gotchas, pointers.

**Keep this file current.** If a change alters the architecture, file layout, data schema, the data-binding attribute vocabulary, or a security-relevant behavior, update the relevant section here in the same change (or PR) — don't leave it to a later cleanup.

## What this is

Physics and We: a bilingual (Armenian `hy` / English `en`) static website for a physics-education program — home, summer camp, our story, interactive labs, study materials (with the laser book), research, news, organisers, sponsors & partners, FAQ, about. **No framework, no build step, no `package.json`/`node_modules`.** Plain HTML/CSS/JS, deployed as-is to **Cloudflare Pages**. Local dev: `npx wrangler pages dev .` (required for `/admin/` — see "Local dev" below).

## Architecture

- `index.html` is the **only real page**. It has no content — just `<link>`/`<script>` tags and three empty slots: `#site-header`, `#app` (main content), `#site-footer`.
- `sections/*.html` are HTML **fragments** — no `<!DOCTYPE>`, `<head>`, or `<body>` — one per page/view. `js/router.js` fetches the right one and injects it into `#app` on navigation (`history.pushState`, `?view=<route>` query param, no full page reload). All fetched fragments accumulate in `#app` at once; visibility toggles via `.view` / `.view.active` CSS classes, not add/remove from DOM.
- `data/*.json` hold **all text**, bilingual side by side per key (`{ "hy": "...", "en": "..." }`). One JSON file per page, paired 1:1 with its `sections/*.html`.
- `js/content.js` binds `data/*.json` values into a fragment's `data-*` attributes (see table below) and defines the inline SVG icon set.
- This layout/text split exists so non-programmers can edit `data/*.json` without touching HTML/CSS/JS (see `Instructions/EDITING-GUIDE.md`).
- **Two themes, dark (default) and light (cream).** All public-site colours are CSS variables in `css/style.css` — dark values in `:root`, light values under `:root.theme-light`, same names (`--bg`, `--bg-3`, `--heading`, `--text`, `--muted`, `--line`, `--accent-2`, `--accent-soft`, `--card-bg`, `--shadow`, …); the light theme has no blue: terracotta replaces blue→violet in the gradients (`--accent` / `--accent-2`) and in small coloured text (`--accent-soft`). `js/theme.js` (loaded in `<head>` to avoid a flash) toggles `theme-light` on `<html>`, saves it to `localStorage.theme`, and fires `theme:changed`; `js/main.js` re-renders the header on it (logo swap + sun/moon button), `js/home.js` (star colours, `STAR_COLORS`) and `js/labs.js` (`palette()` → `ctx.color`) recolour their canvases. The page background is set on both `html.site` and `body.site` on purpose: with only one, it becomes the page backdrop, which Chrome doesn't repaint on a theme switch (the band under the menu on inner pages kept the old colour). Don't remove either.

### Data-binding attributes (`js/content.js`)

| Attribute | Effect |
|---|---|
| `data-text="hero.title"` | plain text from JSON key |
| `data-rich="story.text"` | like `data-text` but supports blank-line paragraphs, `**bold**`, `[text](url)` (an `http(s):` link opens in a new tab with `rel="noopener noreferrer"`, stage 12d; `#…`, `?…` and `/…` stay in the tab; a `)` in an address ends it, so write `%28`/`%29`) |
| `data-list="cards"` | repeats the element's inner `<template>` once per array item |
| `data-icon="icon"` | renders the named inline SVG icon |
| `data-image` / `data-alt` | image src + alt text |
| `data-route="button.route"` | turns element into a link to another page/route |
| `data-route-id="slug"` | links to one specific item on that route (a lab, a news post) |
| `data-link="link"` | turns the element into a link to a website outside this site (opens in a new tab); empty value removes the element, unless it is marked `data-keep`, which leaves the wording as an inert button |
| `data-number="number"` | number that counts up when scrolled into view (`js/anim.js`) |
| `data-ui="learnMore"` | pulls a shared short string from `data/site.json` (`ui` block) |

A missing/empty JSON value **hides** that element rather than rendering empty — a half-finished translation never looks broken.

### Request/render flow

1. Browser loads `index.html` (only time it ever does a full load).
2. `js/main.js` reads `data/site.json` → builds header nav + footer.
3. `js/router.js` waits for `data/site.json` **and** `DOMContentLoaded` (by then every plain `<script>` at the bottom of `index.html` has run, so every page script is listening), parses the route → fetches `sections/<route>.html` + `data/<route>.json`.
4. Fragment wrapped in `<section class="view" id="view-<route>">`, injected into `#app`; `js/content.js` fills in text via the attributes above.
5. `js/anim.js` handles scroll reveals + counting numbers.
6. Router idle-prefetches every other route so subsequent nav feels instant. Those hidden builds also fire `section:ready`, so a page that must wait until it is on screen listens for `view:shown` (`{ detail: { route, id } }`, fired by `activate()` whenever a page comes on screen, after `show()` has scrolled to the top, so a page may scroll to its item then; `id` is the address's `&id=` or null; used by `js/laser-study.js` to download KaTeX only then and to open the book at `id=section-…`, the lab's "Learn more").

Corollary: `<script>` tags inside a `sections/*.html` fragment **never execute** (browsers don't run scripts injected via `innerHTML`). All JS lives in `js/`; page-specific logic hooks the `section:ready` event (pattern: `js/news.js`).

## Critical gotchas

- **Two unrelated `news.json` files.** `news.json` (repo root) = actual news items, written only by the admin panel (`functions/admin/api/publish.js`). `data/news.json` = just the news page's heading/lead text. Never hand-edit the root one.
- **Fragments have no working `<script>`.** Any JS for a `sections/*.html` page must live in `js/` and hook `section:ready`. Load it with a plain `<script>` at the bottom of `index.html` (no `async`, never added later): the router builds the first page at `DOMContentLoaded`, and a script that runs after that misses the first `section:ready`. Before the router waited for it, a slow download of the laser scripts let it build the laser page before `page.js` listened, leaving the bench blank (`page.test.js`, "the router builds the first page only after every script on the page has run").
- **Multi-file additions must stay in lockstep.** New page = entry in `data/site.json` nav + `sections/<route>.html` + `data/<route>.json`. New lab = `js/labs/<slug>.js` (with matching `Labs.register("<slug>", …)` name) + `data/labs/<slug>.json` + a block in `data/labs.json` + a `<script>` line in `index.html`. New laser file = the file + its name in `ENGINE_FILES` or `UI_FILES` (`tests/laser/helpers.js`) + a `<script>` line in `index.html` in that order (`site-files.test.js`, `engine-rules.test.js`). Full walkthroughs: README §2 "Adding a new page" / "Adding a new interactive lab", and `Instructions/LABS-GUIDE.md`.
- **No build step, no dependencies.** Don't introduce a bundler, npm package, or `package.json` casually — this is a deliberate project constraint, not an oversight. The one exception is KaTeX, vendored as plain files in `vendor/katex/` (no npm) and loaded only by the study page; the mutation check does not copy `vendor/` (study.test.js reads it from the real repo).
- **README may reference a third language, `ru` (Russian), in a couple of places** (e.g. the data-attribute/text-format section and the "how do new files connect" section). This looks stale after commit `f956d38` ("Deleted russian") — the site and `data/*.json` are currently hy/en only. Don't trust that specific detail in the README without checking the actual JSON files; fix the README wording if you're already editing that section.
- **Never hard-code a colour.** Every colour must work in both themes: use the theme vars in CSS, `ctx.color.*` in labs, and a per-theme table in JS canvases (see `STAR_COLORS` in `js/home.js`). A literal `#fff` or `rgba(255,255,255,…)` vanishes on the light theme. Deliberate exceptions: white text on the accent gradients (`.btn--primary`, `.step::before`), the white `.partner-logo` tiles, the always-dark `.gallery-lightbox`, the always-light laser lab (`--laser-*` in `:root` only), and the laser page's physical colours in `js/laser/ui/materials.js` (a ruby rod is red in both themes; each colour is made readable on the theme's background and tested for contrast).
- **Labs pages are wrapped in `<div class="line-art">`** (`sections/labs.html`, `sections/lab.html`) for the silver line background. Inside it bands go transparent and cards/the lab panel get a solid `background-color` so the lines don't run through text.
- **`<header>` / `<footer>` inside a fragment inherit the site-wide rules** — `header {}` in `css/style.css` (blue bar, flex) and `body.site footer` in `css/site.css` (footer bar). A content block using those tags must reset them (see `.lab__head` / `.lab__foot` in `css/labs.css`).
- **CSS lives in CSS files only** — no `style="..."` attributes or `<style>` blocks in HTML/fragments; reuse `css/site.css` blocks and `css/style.css` variables before adding new ones.

## Security-sensitive code

`functions/admin/_middleware.js` and `functions/admin/api/*.js` implement the entire auth/authorization layer: PBKDF2 password hashing, HMAC-signed HttpOnly/Secure/SameSite=Strict session cookies, per-IP rate limiting, CSRF/origin checks, field validation on publish, magic-byte validation on upload, and security response headers. Treat changes here as security-critical — cross-check against `Instructions/SECURITY.md` before and after, and don't weaken validation, auth checks, or the deliberate SVG-upload rejection (stored-XSS prevention) without a clear reason.

## Local dev

- Public site only: `python3 -m http.server 8000` → `http://localhost:8000`. Fine for iterating on `sections/`, `data/`, `css/`, `js/` (non-admin).
- Anything involving `/admin/`: must use `npx wrangler pages dev .` — a plain static server doesn't run `functions/`, so the middleware never executes and `/admin/` is broken/unprotected. Requires a local `.dev.vars` (copy from `.dev.vars.example`); default localhost-only login is `admin` / `password` unless overridden.
- Opening `index.html` directly via `file://` (double-click) always shows a blank page — everything loads via `fetch()`, which browsers block on `file://`.
- Laser tests: `node --test` from the repo root (needs only Node; no `package.json`, no npm install). It finds every `tests/**/*.test.js`.
- Laser mutation check: `node tests/laser/mutation-check.js`. It copies what the tests read (`index.html`, `js/`, `css/`, `data/`, `sections/`; never `.git`, `images/` or secrets) to a temp folder, checks that the tests pass on the unchanged copy, then applies each deliberate mistake from `tests/laser/mutations.js` (paths relative to the repo root) to a fresh copy and expects a test to fail. For each mistake it runs the test files one at a time (each with `node --test`, as the suite does) and stops at the first that fails: one failing test makes the mistake caught, so the verdict is the one the whole suite would give, at a fraction of the cost (stage 7c: about 25 minutes before). The files named after the changed file run first (`bench.js` → `bench.test.js`, `bench-pumps.test.js`), then the others quickest first, timed on the unchanged copy (`orderFor`). It checks one mistake per processor core, less one, at once, each in its own copy, and prints the results in list order and the time it took. A test file that fails without reporting any test of its own (Node itself crashed, exit 139: about 1 run in 30 of `page-choose.test.js` on a busy machine, Node 24.14) is run once more; a file that cannot load fails both times, so the verdict is the same (stage 13b; `mutation-check.test.js`). Outcomes: caught / MISSED / TIMED OUT (a test file ran over 60 s before any file failed: a test's work is not bounded tightly enough; see the test gotchas below; a slow file after the one that fails is not run, so it is not reported) / ERROR (bad entry, or a change that is not valid JS/JSON). The tests read the copy through `LASER_TEST_ROOT` plus `LASER_MUTATION_CHECK=1`; `LASER_TEST_ROOT` on its own makes every test stop with an error, so a leftover variable cannot silently test an old copy. The real files are never modified. Its own test is `tests/laser/mutation-check.test.js`.

## Laser simulator (`docs/laser-physics.md`, `js/laser/`)

`docs/laser-physics.md` is the physics spec for the laser simulator; `docs/laser-plan.md` is the architecture and the build stages (with which ones are done). **Every stage follows the recipe in `docs/laser-plan.md` §3** (doc audit, tests first, mutation check, `/code-review`, docs, one commit), and that file's "Doc problems found in the pre-audit" table (D1–D10) lists known traps for later stages. The simulator is one big lab on **its own hidden route `?view=laser`** (like `post` / `lab`), with a parts bench to play with and a "learn" section. It does **not** use the `js/labs.js` shell, whose single canvas and slider column are too small for it.

**Engine rules.** `tests/laser/engine-rules.test.js` enforces the first three:
- Each file is a plain script, `(function (root) { var E = root.LaserEngine = root.LaserEngine || {}; … })(this);`. The same file runs in the browser and in Node's `vm`.
- Only plain numbers and objects go in and out, in SI. The engine must not use the page, network, clock, timers or random numbers. The test bans those globals as whole words (`window`, `document`, `self`, `globalThis`, `fetch`, `Date`, `setTimeout`, `Math.random`, …), with comments ignored, so a name like `brewsterWindowLoss` is fine.
- The only global it adds is `LaserEngine`.
- Load order is listed once in `ENGINE_FILES` in `tests/laser/helpers.js`; a new engine file must be added there (`engine-rules.test.js`). `index.html` must load the engine in the same order (`site-files.test.js`).
- The engine's objects (`check`, `constants`, `units`, `spectrum`, `media`, `cavity`, `ode` and its coefficient tables `ode.tableau` and `ode.rosenbrockCoefficients`, `rates` and `rates.fourLevel`, `rates.threeLevel`, `rates.twoLevel`, `pumps`, `qswitch` and `qswitch.ABSORBERS` and each filter in it, `optics`, `harmonic` and `harmonic.KDP`, and `bench` and `bench.MIRROR_SHAPES`) are frozen with `Object.freeze`; `media.get()` returns a copy.
- **Calling convention:** a function with one input takes it as it is (`cavity.freeSpectralRange(0.3)`); a function with more than one takes **one object of code-named values** (`cavity.thresholdGain({ refl1, refl2, alpha_i, l_g })`), so two numbers cannot be swapped. Every input is checked with `LaserEngine.check` (`check.js`, loaded first): a missing or impossible value throws an error that starts with the function the caller called, and so does a name the function does not use (a typo, or a loss the formula would quietly ignore), even if its value is 0. Pass each function exactly its own inputs, not one shared description object. Tests: `check.test.js`, and the "refuses plain numbers" / "names the function" tests in `spectrum.test.js`, `constants.test.js`, `cavity.test.js`. New engine files use `check.js` too, not their own checks.
- `gamma` is the single-pass loss; `T_oc` and `L_i` are round-trip fractions (γ ≈ (T_oc + L_i)/2 for small losses). A cavity with no loss at all throws (its τ_c, finesse and power would be infinite), and so does a loss too small to divide by (γ = 10⁻³²⁰ in `photonLifetime` and `rates.fourLevel.scales`, T_oc + L_i = 10⁻³²⁴ in `rigrodLowGain`); `rigrodExact` and `finesse` have no internal loss, so `alpha_i`/`L_i` are not among their inputs (`cavity.test.js`).
- Anything that depends on the round-trip time takes the group index: `cavity.effectiveLength({ L, l_g, nGroup })` with `media.get(id).nGroup` (diode 4; its phase index `n` is 3.6) (doc §3.3; `media.test.js`, `cavity.test.js`).
- Below threshold the bandwidth and output-power functions return 0, never `NaN` or a negative number (`spectrum.test.js`, `cavity.test.js`).
- **Every time-dependent part runs on `ode.dopri5` or `ode.rosenbrock`, both `({ f, t0, state0, t1, rtol, atol, h0, hMax, maxSteps, peakOf })` with the same answer `{ t, state, reachedEnd, hNext, accepted, rejected, evaluations, peak }`** (tested in `ode.test.js` and `rosenbrock.test.js`; `peakOf`, optional, names one entry of the state, and `peak` = `{ t, value }` is its highest value at t0 and the accepted points, null without `peakOf`: a giant pulse lasts ~10 ns, far less than a call, and the solver's short steps there see its top; every rule below holds for both, because both run on one step loop, `adaptiveRun`, and differ only in how they try a step):
  - the state is called `state`, not `y`, because y is the inversion of §11.2;
  - `maxSteps` counts every attempt, accepted or rejected. Its default (100 000) is only a safety limit, several frames long (~65 ms for a 2-component `f`), so the page must pass its own per-frame budget. Running out returns the last accepted point with `reachedEnd: false`; passing the returned `hNext` as `h0` carries on with the steps one long call would take (except right after a rejected step, where a new call may let the next step grow sooner), and a short frame does not shrink `hNext`. For no step limit, leave `hMax` out (`Infinity` is refused);
  - `f` gets a copy of the state and its answer is copied, so it cannot corrupt the solver. `f` is never called outside [t0, t1], not even one rounding unit past t1, so an `f` that switches at t1 only sees its own side;
  - `f` not finite at the start throws at once. A trial step with a value that is not finite (NaN from `f`, or a state overflowing to Infinity) is retried 5× shorter, and a step that has to shrink below the float resolution of t throws (blow-up, NaN, or tolerances too tight), so a NaN never just burns the budget. Error messages from `check.describe` show strings in quotes and arrays by their length;
  - `dopri5` is explicit: a stiff problem costs about |λ|·(t1 − t0)/3.3 steps however smooth the answer (§11.3; the stiff test measures it). The laser below threshold is such a problem (∂ṡ/∂s = −(1 − y)/ε), so the bench uses `rosenbrock`;
  - `rosenbrock` (Shampine & Reichelt 1997, the formulas in `docs/laser-plan.md`, stage 7a) is L-stable: its cost does not grow with the stiffness (λ = 10⁴ and 10⁸ about 800 steps each). It finds J = ∂f/∂state and T = ∂f/∂t by differences once per accepted point (n + 1 calls of f; T forward over at most the step, as MATLAB's ode23s takes it, so f still never leaves [t0, t1]) and keeps them for the retries; a try costs 2 calls and solves W = I − h·d·J by Gaussian elimination with pivoting. It is order 2 and its new state is the less accurate of its pair, so its error at the end of a long run is hundreds of times rtol (`dopri5`: a few times); in smooth, non-stiff stretches it takes more steps (Nd:YAG lasing: 3×). Because it differentiates f, f must be smooth where the solver runs: a kink with a huge slope on one side stops it (the seed floor below).
- **Rate equations** (`rates.fourLevel`, all tested in `rates.test.js`):
  - the state is `[y, s]` with y = N/N_c and s = ln p (§11.2, §11.3); time is t′ = t/τ. Start from one photon, `s = scales(...).sOnePhoton`: s = ln 0 does not exist;
  - physical values are multiplications by `scales(...)`: N = y·`N_c`, φ = p·`phiPerP`, P_out = p·`powerPerP`, t = t′·τ. `scales` takes the mirrors and α, not γ, so γ and the output coupler cannot disagree; it repeats `cavity.js`'s one-line γ, and a test keeps the two equal;
  - `derivatives({ x, eps, beta })` checks its inputs once and returns an unchecked f for the solver. The seed βy·e^(−s) is computed as one exponential, e^(ln β + ln y − s): e^(−s) alone overflows past s ≈ −709 while the seed is about 1 (pump off). With β = 0 the seed is 0, not 0·Infinity = NaN. The seed counts y as max(y, 0) + 10⁻¹² (`Y_FLOOR`; `liftToSeed` and `steadyState` use the same): with no seed at y ≤ 0, the seed's slope just above 0 (β·e^(−s)) grew past 10³³ with the pump off and stopped the implicit solver, and max(y, 10⁻¹²) moved that corner to 10⁻¹², where the Jacobian's difference in y reaches across it (pump-off frames cost up to 580 steps; stage 7a review). Added, the corner is at y = 0, which a decaying y never crosses. So with the pump off the photons settle at p ≈ β·10⁻¹² instead of following the atoms down (`rates.test.js` checks the slope across 10⁻¹², `bench.test.js` the frame cost);
  - ln p is too stiff to integrate when the photons are far below the seed (p ≪ βy): after β is turned on following a β = 0 run (s may be −300), the solver throws "the step size fell below". So the bench passes the state through `liftToSeed({ state, beta })` before every solver call: it raises s to ln(β·(max(y, 0) + 10⁻¹²)) and leaves a running laser, the below-threshold level, the one-photon start and β = 0 unchanged. Behind a closed Q-switch, which loses 1 + q times as much, the bench passes β/(1 + q_now): lifted to the open cavity's level, the photons fell back in every call (64 steps a call behind Nd:YAG's closed cell; 4.4 with it; `bench-qswitch.test.js`, the page frames behind the closed switch);
  - `relaxation` throws for x ≤ 1 (there is nothing to oscillate around). This is unlike the bandwidth and power functions, which return 0 below threshold;
  - a small oscillation in ruby is tiny: δy ≪ √(ε(x − 1)) ≈ 2×10⁻³. A 1 % kick is full spiking, with a period about twice as long.
- **Three and two levels** (`rates.threeLevel`, `rates.twoLevel`, all tested in `three-level.test.js`; doc §4.1, §11.2):
  - y = ΔN/N_c runs from −n_t (every ion down) to n_t, with n_t = N_t/N_c; the pump is w = W_p·τ, **per ion of the unpumped medium** (a lamp sets W_p whatever the populations), and may be a function of t′ like four levels' x (a flash). `threeLevel.scales` takes four levels' nine inputs plus `N_t` and gives p = 2Bτ·φ (one emission changes ΔN by 2: drop the 2 and ruby's output doubles), `n_t` and `wThreshold` = (n_t + 1)/(n_t − 1), null for n_t ≤ 1. Two levels use the three-level `scales` and `liftToSeed`; they have only `derivatives` and `steadyState` of their own;
  - three levels: dy/dt′ = w(n_t − y) − (n_t + y) − y·p; two levels: −2w·y − (n_t + y) − y·p (the pump's light drives the ions back down as fast as up, so y < 0 always). **The seed comes from N₂ ∝ n_t + y, not from ΔN** (D2: ΔN is negative until half the ions are up);
  - the seed floor is `ION_FLOOR` = 10⁻⁷·n_t, not four levels' 10⁻¹²: near y = −n_t, n_t + y is known only to the rounding of n_t, and next to 10⁻¹² that rounding made the implicit solver take 10⁵ steps per 10τ as the ions fell back (now under 10). `liftToSeed` raises s to ln(β(max(n_t + y, 0) + 10⁻⁷·n_t)/(1 + n_t)): the 1/(1 + n_t) keeps it below the below-threshold level β(n_t + y)/(1 − y), so it never raises a steady state;
  - `threeLevel.relaxation` linearizes the three-level equations: ω_R² = p₀/(ττ_c) with p₀ = (n_t − 1)w − (n_t + 1), damping rate n_t(w − 1)/(2τ). Ruby at x = 3: a 5.1 µs period and 0.2 ms damping, not §4.2's four-level 17 µs and 2 ms; it throws for n_t ≤ 1 and at or below threshold.
- **Pumps** (`pumps.js`, tested in `pumps.test.js`): `flash({ energy, flashTime })` returns power(t) = (E/t_p)(t/t_p)e^(−t/t_p), 0 for t ≤ 0 (∫ = E, peak E/(e·t_p) at t_p), checked once like `derivatives`. `dischargeGain({ law, current, currentPeak, gainPeak })`: `"optimum"` is §6.4's ΔN = aI/(1 + I/I_sat) − bI with a/b = 4 (`gainRatio`), scaled to gainPeak at currentPeak and 0 again at 3·currentPeak (He-Ne, CO₂); `"square"` is gainPeak·(I/currentPeak)² up to the rated currentPeak (Ar⁺). `dischargeThreshold` (null if the tube never reaches g_th) and `dischargeMax`; a current past the max throws.
- **The bench** (`bench.js`, tested in `bench.test.js` (the Nd:YAG diode bench), `bench-pumps.test.js` (every other medium and pump) and `bench-qswitch.test.js` (the Q-switch)):

Only pairs common in practice are benches (the owner's choice, stage 12c: no green-laser or violet-diode ruby, no lamp- or diode-pumped Ti:sapphire); gases only take a discharge. CaF₂:Dy (no σ) and the diode laser (its own carrier model, stage 13f) have none: `pumpsFor(medium)` gives `[]` and `configFor` throws "cannot be simulated yet". `configFor({ medium, pump })` returns a new config, `controls(config)` its sliders: `pump`, the config field the pump slider sets and its range (`pumpPower` W, `flashEnergy` J or `current` A; a discharge's top is its law's `dischargeMax` for the config's own `currentPeak`), and `coupler`, T = 1 − R₂ from 0.5 % to 60 % (log) for every bench, so ruby's 50 % fits.   - `derive(config)` takes one config object: `medium`, `pump`, `l_g`, `area`, `L`, `refl1`, `refl2`, `alpha_i`, `beta`, and by pump kind `pumpPower`, `pumpLam`, `eta` (diode, laser), `flashEnergy`, `flashShare`, `flashTime`, `pumpLam`, `eta` (flashlamp; `flashShare` is the share of the lamp's light the rod absorbs) or `current`, `currentPeak`, `gainPeak` (discharge). `pumpPower` is **absorbed** power spread evenly over area·l_g (§4.1's plane-wave model; for a matched spot this is §6.3's Fan–Byer threshold). - **The mirrors** (`optics.js`, `bench.js`, stage 10a; `optics.test.js`, `bench-mirrors.test.js`; doc §5.9, §7.7):
  - sign conventions (D9): optics.js takes signed curvatures c = 1/R, positive for a concave mirror, negative for a convex one, 0 for a flat one (a flat mirror's R = ∞ cannot be passed: `check.js` refuses Infinity); a mirror is a lens of f = R/2; `focus1`/`focus2` are R/2, positive in front (real), negative behind (virtual), null for a flat mirror;
  - the rod sits in the middle of the cavity and counts l/n for the beam (D10): the pair acts as an empty cavity of L* = L − l_g + l_g/n, and g = 1 − L*·c; `waistAt` and `beamRadius` use real distances from mirror 1;
  - the config has `mirror1`, `mirror2` (`"flat"`, `"concave"`, `"convex"`: `bench.MIRROR_SHAPES`), `Rc1`, `Rc2` (positive radii, m; a flat mirror keeps its radius unused, for the page's slider) and `aperture` (the rod's or the bore's radius, taken at both mirrors). Each `SETUPS` bench has its real mirrors (§5.9: ruby and Nd:glass flat-flat, He-Ne flat and 45 cm, …);
  - the mirrors' loss per round trip (§7.7): each mirror loses min(e^(−2a²/w²), Vainshtein's flat-mirror loss at the same Fresnel number), with |Y| outside the stable region so the loss runs on across every edge, and an unstable pair keeps 1/M² more. The min is the simulator's own interpolation, written as such in the doc. Only TEM₀₀, mirrors aligned;
  - **the mirrors change only the losses, not the gain** (D15): `derive` passes α_i + γ_m/l_g (`alphaWithMirrors`) wherever the internal loss was used (`rates.*.scales`, `thresholdGain`, the best coupler's L_i), so γ = the old γ + γ_m; the gain stays spread over `area`. `derive` gives the whole `optics.resonator` answer as `resonator`;
  - `resonator` gives no Gaussian mode (null `w0`, `waistAt`, `zR`, `w1`, `w2`) on the stability edges and outside them; the confocal point g₁ = g₂ = 0 is stable. `traceRay` runs at most 10 000 round trips.
  - **the thermal lens** (stage 13c; `thermal.test.js`; doc §7.3, §8.7): `roundTrip`, `resonator`, `beamRadius` and `traceRay` take `lens`, the power 1/f (m⁻¹, any finite number, 0 = none) of a thin lens at the rod's middle (reduced ½·L* from each mirror); with `lens: 0` the old code runs unchanged. With a lens: Kogelnik's equivalent resonator (L₀ = 2d − d²P, g_i = 1 − dP − L₀c_i; the stability diagram's dot is these g's), the spots' clip loss with |L₀| (`fresnel` and the Vainshtein bound keep L*), the beam as two Gaussian pieces carried by q from the round trip; `w0`/`waistAt` are then the narrowest place between the mirrors (a waist, the lens or a mirror), and each hit of `traceRay` has `middle`, the height where the ray crossed the lens (none without a lens). The bench makes the lens only for a steady pump (diode, laser) on a medium with `thermalK` and `dndT` (`media.js`; only Nd:YAG: 14 W/(m·K), 7.3×10⁻⁶ K⁻¹), `hasThermalLens({ medium, pump })`: 1/f = (1 − η·λ_p/λ_l)·P_abs·(dn/dT)/(K·area), at once (no thermal time); `derive` gives `thermalFocus` (m, null without a lens or with the pump off), and its `resonator`, `beamPath`, γ_m, threshold and x all have the lens, so the threshold is the cavity's at the pump set now. `readConfig` works out the lens once (`read.lens`) and the mirrors with it (`mirrorsOf`) after the pump's checks;
  - for the page (stage 10b): `controls(config)` also gives `Rc1`, `Rc2` (`{ name, min: L/4, max: 50, log: true }`, null for a flat mirror); `beamPath({ config, starts, roundTrips, points })` gives `{ mode, rays }`: the mode's radius `{ z, w }` at `points` + 1 places from 0 to exactly L (null without a Gaussian mode) and `traceRay` from mirror 1 at each height of `starts` (|y| ≤ aperture), θ = 0; at most 100 round trips and 1000 points (`bench-mirrors.test.js`).

The chart reads the history's points (`{ t, P }`) directly; a piece whose `advance` `peak` lies strictly inside it adds that point before its end, so a giant pulse shows at its true top (stage 8b). `axis.js` builds powers of ten with `Number("1e" + k)` and cleans products to 12 digits, so a tick is 0.3, not 0.30000000000000004.
- **Each medium's look and the beam's colour** (`materials.js`, `draw-bench.js`, stage 10c1; `materials.test.js`, `draw-bench.test.js`): `page.js` gives the drawing `light.medium` (the engine's id) and `light.lam` (its wavelength, from `media.get`, once per config). `materials.MEDIA[medium]` is `{ look, body }` (doc §5.10): `rod` (ruby, Nd:glass, Nd:YAG, Ti:sapphire) is drawn as a crystal cylinder (its colour, a darker bottom, a `HIGHLIGHT` strip along its top, an ellipse end face at each end; the shade is `SHADE`, black at low alpha), `liquid` (dye) as a glass cell inside the rod's outline with two pipes under it (`layout().cellPipes`), `gas` as `GLASS` with the bore glowing in its body colour while the current flows. The beam (rays, hourglass, light leaving) is `materials.beam(lam)` (Bruton, 380–780 nm), or `INFRARED`, a false colour, with "1.06 µm · infrared, invisible" (`labels.infrared`, or `labels.ultraviolet` by `beam(lam).band`) on its own row under the pump's name. Coloured rays are drawn over a 2 px wider casing in `colors.bg`, so they show over a medium of their own hue. Every physical stroke and beam goes through `materials.readable(colour, colors.bg)`: mixed towards white or black until its WCAG contrast is at least 3.3 (so 3 against both ends of the bench's box); fills at partial alpha keep the raw colour. The two-level atom (no entry in `MEDIA`), or a light without `medium`, keeps the theme's colours.
- **The mirrors on the bench** (`draw-bench.js`, stage 10b; `draw-bench.test.js`): each mirror is drawn as a real one seen from the side, whatever the medium: a block of pale green optical glass (`materials.MIRROR_GLASS`) with a white glint and a darker back edge, a silver coating on its face (`materials.SILVER`, solid on the back mirror, thinner and see-through on the output one), held in a metal mount (`MOUNT_PLATE`) with an adjusting knob at the top and the bottom and a hole for the light (`mountHole(L)`: the plate stops `MOUNT_HOLE` px short of the rays, the rod's or bore's half-height and the pump's cone, which pass the mirror) (rectangles: a circle on the bench counts as a photon in the tests); with `light.cavity` = `{ length, aperture, shapes: { back, output }, focus: { back, output }, mode, rays: [{ y0, hits, escaped }] }` the mirrors are drawn flat, concave or convex (`SHAPES`; `faceX(L, which, y, shape)`), every face standing out of the glass towards the laser, never into it (a concave one a cup: its rims out, its middle on the glass; a convex one its middle out), as deep as `light.cavity.curve` says (0 for the radius slider's largest radius, 1 for its smallest, from `page.js`'s `curveOf` on the slider's log scale; between the layout's `sagMin` and `sagMax`, else `sag`), the beam is the mode's hourglass (a band half the aperture wide without a mode), the traced rays go bounce by bounce, fading 0.72 a round trip, clipped to a band a quarter of a mirror above and below the mirrors, and a ray that walks out goes on for 6 % of the width. The aperture is drawn as the rod's half-height (`layout().apertureHalf`), or the bore's on a discharge (`boreHalf`), so the beam and the rays stay inside the medium that limits them; "Widths × k" (`labels.widths`) says how much wider than true. F₁ (back) and F₂ (output) are dots on the axis (solid real, dashed hollow virtual) or, off the picture, an arrowhead in the margin (filled real, outlined virtual) with "F₂ 500 mm" just inside the mirror on that mirror's row (`focusRows`), no wider than `focusRoom` (to the rod, or a discharge's electrode). Without `light.cavity` the old parallel rays below are drawn. `page.js` builds the cavity from `derive`'s `resonator` and `bench.beamPath` (4 rays at ±0.9, ±0.45 of the mode's half-width on mirror 1, 4 round trips, 40 pieces) only when one of `CAVITY_FIELDS` changes; its readouts: the pair stable, unstable or on the edge (|m| within 10⁻⁹ of 1), the narrowest radius between the mirrors (w₀ when the waist is between them, else the smaller mirror spot), the mirrors' round-trip loss ("< 0.01 %" under 10⁻⁴), and on a bench with a thermal lens (`bench.hasThermalLens`) its focal length (`thermalLens`, "—" with the pump off; stage 13c) (`page-mirrors.test.js`). The drawing's cavity is worked out again when one of `CAVITY_FIELDS` or `derive`'s `thermalFocus` changes, so a pump move retraces it only on a bench with a lens; a traced ray whose hit has `middle` is drawn bent at the cavity's middle (`draw-bench.test.js`).
- **The bench's rays** (`draw-bench.js`): an odd number (3–21, 5 px apart or more) from one mirror's curved face to the other's (`faceX`), arrowheads right on every second ray and left on the others; `raysOut(count, T)` = round(count·T), at least 1, of the rays nearest the axis go on to the edge of the canvas. Their alpha is `rayAlpha(beam)` = √(output ÷ output at twice threshold), at most 1, so spontaneous emission (10⁻⁸) shows no beam. `labels` holds words only: the drawing writes "Transmission 5.00 %" itself from `light.transmission`, on its own row under the output mirror's name (under the bench, beside the pump's name, the Armenian was squeezed to 40 % on a phone).
- **The pumps on the bench** (`draw-bench.js`, stage 7d; `draw-bench.test.js`): `light.pumpKind` is one of `LaserUI.bench.KINDS` (`diode`, `laser`, `flashlamp`, `discharge`, the engine's pump kinds; `page-choose.test.js` checks the drawing knows every one); none or an unknown kind draws the diodes. A pump under `PUMP_OFF` (1 % of full) is drawn off: a flash's tail reaches 0 only after hundreds of t_p. Diodes (stage 10c2, end-pumped, §6.3): a module with fins on the bench under the rod (`layout().diodeModule`), a fibre along the bench and up the left margin to a lens on the axis behind the back mirror (`fibre`, `lens`), and, while on, a cone (`cone`) through the back mirror into the rod fading as e^(−z/d) in slices, d = `PUMP_DEPTH` (0.35) of the drawn rod, an illustration. Flashlamp: a tube there with a metal cap at each end, glass edge and caps in `colors.lamp` (`--laser-canvas-lamp`, steel, the same in both themes since the near-white lab of 2026-11-20; before it a per-theme sky blue or terracotta), dark before Fire. Lit (stage 8b, the owner asked for a flash that is easy to see; `draw-bench.test.js`), all of it as strong as `light.pump`: the whole canvas tinted with `colors.flash` (`--laser-canvas-flash`, a silver-white, the same in both themes; the canvas tint, the halo and the beams use it raw, as a faint glow, while the streaks, the burning gas and the flash's pump photons use `materials.readable(colors.flash, colors.bg)`, as the raw colour is about 1.6:1 on the lab's near-white) at 0.1·pump before any part (`flashBehind`), a halo of `HALO_RINGS` (6) ellipses round the tube growing by `layout().haloStep`, broad beams (a filled quadrilateral) from the tube's lit length to the rod's whole bottom, `FLASH_STREAKS` (16) streaks round the tube that flicker in screen time `view.t` (a view without a number t draws as t = 0; with `view.still`, a visitor who asked for less motion, they stand still as at t = 0), the gas burning in `colors.flash` with a canvas shadow bloom (`shadowBlur` = `layout().bloom`·pump, inside its own save/restore so nothing else blooms), arrows into the rod in `colors.accent`, and the rod tinted by the flash it absorbs (`lightRod`). Discharge: no rod; the medium is a gas tube over 0.86 of the cavity, as tall as the rod, every ray inside its bore, its gas glowing with the current (alpha at most 0.75, so the rays stay visible); electrodes under its ends are wired to a supply on the bench, with an arrow on each wire while the current flows, and its posts stand outside the electrodes so no wire crosses one. Pump laser (stage 10c2, end-pumped as real Ti:sapphire and dye lasers are): a box on the bench under the rod's middle (`layout().pumpLaser`, where the diodes' module stands), its beam (only while the pump is on) along the bench to a `periscope` of two 45° mirrors on a post in the left margin, up to the axis, into the diodes' `lens`, then the same cone and photons as the diodes; a filter on such a bench stands beyond the rod too. The rays' arrowheads sit in the gaps between the mirrors and the medium (the rod, or the gas tube). Every part is in `layout(w, h)` and checked at every width. The pump's light (stage 10c2): a diode's or a pump laser's colour is `materials.beam(light.pumpLam)` made readable (`page.js` passes the config's `pumpLam`; 532 nm green for dye and Ti:sapphire), a flashlamp's `colors.flash`, without a medium `glow`; an invisible pump joins the note ("808 nm, 1.06 µm · infrared, invisible"). Pump photons (`PUMP_PHOTONS`, 12; diodes, pump laser, flashlamp), as many as `ceil(12·pump)`, travel into the medium in screen time and vanish at an exponential depth where a `HIGHLIGHT` spark lights an atom; a gas tube has `GAS_ATOMS` (18) drifting in its bore, `round(18·pump)` lit. Both come from fixed fractions (no random numbers), stand still for `view.still`, are drawn after the rays, each dot on a ring of `colors.bg` (a white spark's ring is `colors.heading` where white would not stand out: the cream theme). An invisible pump is `materials.PUMP_INFRARED`, paler than the laser's `INFRARED`. Unlit gas atoms are `colors.muted`.
- **The photon cartoon** (`draw-photons.js`) is an illustration, not physics: no number on the page comes from it. `LaserUI.photons.create({ cols, rows, random })` holds 60 atoms and at most 48 photons; `step(dt, { excited, light, pump })` runs in **screen** time once a frame (not while paused), with `excited = y/(1 + y)` for four levels (half the atoms at threshold) and N₂/N_t for three and two, `light` = `LaserUI.bench.rayAlpha` of the same beam, `pump = min(1, level/4)` with the level from `bench.pumpNow`'s x (the bench's pump glow is the same number). A laser photon passing an excited atom of its row has a 0.45 chance of making it emit a twin beside it; an atom emitting by itself sends a stray photon in a random direction (within 0.2 rad of the axis it joins the laser light). `random` is passed in: `page.js` gives `Math.random`, the tests a seeded, constant or scripted source. It lives in `state`, so it survives a language switch; Reset makes a new one.
- **Time:** each frame moves the simulation dt / slow motion (10³–10⁹; each bench starts at its own, `START_SLOW_MOTION` in `page.js`, from 10³ for the two-level atom's laser to 10⁷ for Ar⁺ and dye), in pieces (one plot point each) that share 1500 solver steps: about 480 points a second of screen time (8 a frame at 60 Hz, 2 at 240 Hz, at least 1), so the plot does not depend on the refresh rate. When the steps run out the simulation falls behind; the `behind` note shows when more than a quarter of a second's frames fell behind (judged once a second, so a dropped frame does not make it blink) and hides on Pause, Reset and a slider move. Measured: about 1 µs a step in Chrome, 6 µs in Node's vm (`dopri5`; `rosenbrock` is about the same per step). Since stage 7a no Nd:YAG setting falls behind on its own (at most about 700 steps a 60 Hz frame, 212 after the pump goes off; `bench.test.js` runs that corner frame by frame with 1.5× headroom), so the page tests of the budget use `dearer()` in `page-helpers.js`, a stand-in solver that costs a set number of steps per simulated second. Stage 7c measures every bench with the real engine at its starting slow motion, 30 frames at each corner of the pump and coupler sliders and 10 more with the pump off (worst 60 Hz frame 739 steps, the two-level atom with a laser; ruby 647), and `page-choose.test.js` bounds each at about 1.5× its own worst. Live readouts are written at most every 0.1 s; a slider move, Pause and Reset write them all.
- **Errors:** an error in a frame pauses the loop (`loop.js`) and `page.js` then sets the button to Play, so Play tries again; a build that throws part-way takes its loop and listeners down before passing the error on (`page.test.js`). `LaserUI.format` writes a value below 1 f of its unit as "< 1 fW" and `number()` writes one below 10⁻¹⁵ as "8.00e−170": `toFixed()` throws past 100 decimals (before stage 7a's seed floor the page met 10⁻¹⁷⁰ W with the pump off; now about 5×10⁻²⁰ W). `format.test.js` tries every power of ten from 10⁻³²³; the page test of the pump off only reaches the floor's level.
- **The experiment survives rebuilds:** `state` in `page.js` (the chosen config, sim, chart history, the photon cartoon, slow motion, playing, the peak since Fire, the flash threshold) lives outside the build, so a language switch changes only the words. The history holds 16384 points (2400 up to 480 Hz, one a frame above, and at most as many again for the pulses' tops; 4096 at 8 a frame once cut the plot short on a 120 Hz Mac); its times must not go back (Reset clears it), so `points(from)` walks back from the newest instead of copying the whole buffer.
- The fake browser's elements have `textContent`, `value`, `hidden`, attributes, children (`appendChild`, `removeChild`, `firstChild`; `document.createElement`, for the dropdowns' options) and listeners (`fire(type, properties)`, e.g. `fire("pointermove", { offsetX: 200 })`; `listenerCount(type)`), and record `scrollIntoView` calls in `scrolledTo`, so the tests check that a teardown removes every slider, number-box, button and pointer listener. Objects made inside the sandbox (an options object, an array) fail `deepEqual` against Node literals: compare their fields or their JSON.
- Words on the canvas come from `data/laser.json` via `Content.inLang` (the label names are `LaserUI.bench.PARTS`), drawn with `fillText(text, x, y, maxWidth)` so a long word is squeezed, not overlapped; `layout(w, h)` is checked for every width from 280 to 1400 px, including that the picture is symmetric (`draw-bench.test.js`). Each canvas's screen-reader name is its `<name>.alt` (`bench`, `power`, `photons`), else the page title, else the canvas is `aria-hidden` (`page.test.js`). Every `{ hy, en }` in `data/laser.json` must have both, and every `data-text` in `sections/laser.html` must exist in it (`site-files.test.js`).

- **Source:** D. V. Sivukhin, *General Course of Physics*, Vol. IV *Optics*, §§119–126, plus standard laser-physics formulas (Svelto, Siegman, Koechner) where the book only describes things in words. Formulas copied from the book keep its equation numbers, e.g. (120.2).
- **Units:** all SI, so formulas can go straight into code. Sivukhin uses Gaussian/CGS units; §13 has the conversion.
- **Symbol table (§0):** every quantity has a fixed **code name** (`N1`, `N2`, `dN`, `sigma`, `tau`, `g0`, `gth`, `refl1`/`refl2` = mirror reflectivities, `Rc1`/`Rc2` = mirror radii, `tau_c`, `w0`, `zR`, `q`, …). Use these names in the lab's JS. Some letters mean different things in different sections (`g`, `R`), and the code names keep them apart. Photons have two names: `phi` (φ) is the **count** in the laser mode (§4, §11), and `S` is the **density** in m⁻³ (§2, §5.7, §9.4), with φ = S·V. Mixing them is off by the mode volume.
- **Section map:**
  - §0: model overview and the layer table (quantum → medium → resonator → pump → beam → polarization → nonlinear). Also a key point: a lens cannot turn lamp light into a laser beam.
  - §1–4: emission and cross section, 3- and 4-level inversion, resonator threshold/modes/power, rate equations (spiking, Q-switching, mode locking).
  - §5: gain media, with a parameter table in §5.1 (ruby, Nd, CaF₂:Dy, He-Ne, Ar⁺, CO₂, diode, dye, Ti:sapphire); §5.9 the mirrors of each bench, with sources.
  - §6: pumping. §7: mirror stability, Gaussian mode, ABCD matrices; §7.7 the loss near and beyond the stability edges (Vainshtein, clipping, Siegman's 1/M², the simulator's interpolation). §8: lenses and beam optics. §9: polarization and Q-switches. §10: nonlinear optics.
  - **§11: from physics to simulation.** The design to agree on before writing code: simulation state, dimensionless equations, numerical scheme, ray tracing, colour from wavelength, on-screen indicators.
  - **§12: test values.** Inputs with expected outputs; use these to check the simulator.
  - §13: constants and CGS ↔ SI conversion.
- **Numerical traps called out in §11.3:** the rate equations are stiff (τ_c/τ goes down to ~10⁻⁶), so a fixed-step RK will not work; use an adaptive or implicit integrator. Integrate `ln p` instead of `p` to avoid overflow. Show time with a slow-motion factor and log axes.
- **Colours:** §11.5 turns wavelength into RGB. Beam colours computed this way are physics, not theme colours, so they are allowed. Everything else on the canvas (background, axes, labels, mirrors) must still use the theme colours, read from the CSS variables as `palette()` in `js/labs.js` does (see "Never hard-code a colour"). Check that the beams can be seen in both themes; a yellow or green beam can disappear on the cream background.
